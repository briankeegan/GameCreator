# What a Clubhouse run is allowed to cost

How the autopilot's context is built, and why it is built that way. Written
after a month's API budget went in a day.

---

## The measurement first

Every run used to receive the entire thread, verbatim. Dog Punk's PR #20, at
about 60 comments, breaks down like this — measured from the comments
themselves, not estimated:

| kind | count | share of bytes |
|---|---|---|
| Claude's own replies | 22 | **76%** |
| live-progress panels (`**Claude is working:**`) | 6 | **19%** |
| retry + failure notices | 12 | 3% |
| **the owner's messages** | 20 | **2%** |

Three things fall straight out of that table, and they are the whole design:

1. **A fifth of the thread is pure noise.** "That run hit a snag — retrying
   automatically (attempt 2 of 3)" and a live-progress panel listing every
   file a previous run touched have no value to a future run whatsoever. They
   are machinery reporting on itself.
2. **The instructions are 2% of the bytes.** Everything the owner has ever
   asked for fits in about a kilobyte. It is the single most valuable content
   in the thread and it is nearly free to carry.
3. **Claude's own replies are three quarters of the cost.** They are long
   because they explain reasoning, and that reasoning is worth almost nothing
   to a later run. What survives is the fact: *the rat sheet was regenerated
   onto the standard*, not the four paragraphs about why.

---

## The rules

**1. Drop noise entirely. No model required.**

Deleted before anything else looks at them, by pattern:

- `**Claude is working:**` live-progress panels — ephemeral status, and the run
  that wrote one has already finished.
- "That run hit a snag — retrying automatically" notices.
- "Something went wrong while handling that" notices, and the out-of-retries
  message.
- Version stamps (`[v0.529]`) and the `_Generated by Claude Code_` footer.

This is deterministic, costs nothing, and removes ~22% before a single token is
spent. Anything deterministic must be done before anything probabilistic.

**2. Never compact the owner's messages.**

They are 2% of the bytes and 100% of the instructions. They are also where the
standing preferences live — "when I say trigger it, send my words verbatim",
"art is generated as sheets" — and those were *stated once, in passing, and
must hold forever*. Summarising them is how a preference silently stops being
honoured. Every one is carried verbatim, always, however old.

**3. Compact Claude's replies with Haiku — once each, then cache.**

This is the 76%, and the only content worth spending a model on. Each reply is
compacted **per comment**, keyed by its comment id, and the result is cached
across runs. A reply is therefore summarised exactly once in its life, no matter
how many runs read the thread afterwards.

Compacting the whole old block afresh every run — the first version of this —
pays Haiku repeatedly for the same unchanged text and produces slightly
different output each time. Per-comment caching means a typical run makes
**zero** Haiku calls, because every comment but the newest has been seen before.

**4. Keep the recent exchange verbatim regardless.**

The last ten messages are passed through untouched. A run has to work out which
messages are still unanswered, and it does that by looking back past its own
last reply — so the verbatim window must reliably contain one. Six was tried
first: this thread had five consecutive owner messages with only failure
notices between them, and six would have cut into the middle of that.

**5. Never let this break a run.**

No API key, API down, malformed response, timeout, corrupt cache — every path
falls back to a plain tail of the thread and continues. A summariser that can
stop a message being answered is worse than an expensive prompt.

## What it costs

On a 60-comment thread:

```
  raw thread                                        ~52 KB
  after dropping noise                              ~41 KB   (deterministic, free)
  owner messages, verbatim                           ~1 KB   (never compacted)
  Claude replies, compacted ~8:1 and cached          ~5 KB   (paid once per comment, ever)
  last 10 messages, verbatim                        ~12 KB
  ------------------------------------------------------------
  delivered to the run                              ~13 KB
```

Haiku calls on a typical run: **zero to one** — only genuinely new comments are
uncached, and the newest ten are verbatim anyway, so a new comment is usually
only compacted much later, when it finally falls out of the verbatim window.

---

## What is deliberately NOT done

- **No summary of the summaries.** A digest of digests loses the specific
  instruction, which is the one thing that has to survive.
- **No dropping of old owner messages, ever.** Age is not evidence that a
  preference expired.
- **No compaction below the budget.** A thread under 12 KB is passed through
  untouched: compressing it saves nothing and costs exactness.
